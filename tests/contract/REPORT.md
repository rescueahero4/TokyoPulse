## Important: check 16 (response time) is flaky across runs — do not read the clean run above as "no performance problem"

Repeated runs during this investigation did **not** consistently pass B16. An earlier
run (same code, same machine, minutes earlier) failed it:

```
[FAIL] B16: slowest endpoint: /impact/Toei-Mita (5844ms); 2 endpoint(s) >= 3s
...
DEFECTS:
  - [A3] api/main.py or api/graph.py: /health took 4.5s (>= 3s) -> FIX: ...
  - [A3] api/main.py or api/graph.py: /impact/Toei-Mita took 5.8s (>= 3s) -> FIX: ...
```

To separate "flaky network to Aura" from "a real code defect", `/impact/Toei-Mita` and
four single-round-trip endpoints were each sampled ~4-8 times outside the validator
script, back to back:

| Endpoint | Samples (seconds) | Round trips to Neo4j per request |
|---|---|---|
| `/health` | 0.38, 0.53, 0.59, 0.85, 2.83, 3.9, 4.5, 6.9 | 1 |
| `/events.json` | 0.38, 0.41, 0.8, 1.0, 1.1, 1.3, 2.6, 3.2 | 1 |
| `/lines.geojson` | 1.2, 1.8, 1.9, 2.4, 2.9, 3.6 | 1 |
| `/stations.geojson` | 0.7, 1.0, 1.1, 1.2, 1.4, 2.1, 5.6 | 1 |
| **`/impact/Toei-Mita` (and other lines)** | **3.0, 3.2, 3.5, 3.9, 4.0, 4.1, 4.5, 4.6, 4.8, 5.0, 5.2, 5.3, 5.4, 5.5, 5.8, 6.1, 9.2** | **4-6 (see DEFECTS)** |

The single-round-trip endpoints are *noisy* (0.4s-6.9s depending on the moment) — that
noise is Neo4j Aura free-tier network latency from this environment, not a code bug,
and most samples for those endpoints land comfortably under 3s. `/impact/{lineId}` is
categorically different: across every sample taken (17 total, spanning three separate
investigation sessions), it was **never once under 3s**, and its minimum (3.0s) is
already at the budget. That is because, unlike every other endpoint, a single
`/impact/{lineId}` request makes 4-6 *sequential* round trips to Neo4j
(`api/graph.py` `fetch_impact()`: a Line lookup, a Station lookup, a Ward lookup, an
Events lookup, and then an internal call to `fetch_line_status()` which itself issues
two more queries) — so it inherits the single-round-trip latency distribution above,
multiplied 4-6x, with no caching. See DEFECTS (ranked #1) for the fix.

One `/impact/Toei-Mita` request during this investigation also failed outright with
`[WinError 10054] An existing connection was forcibly closed by the remote host` —
a transient Aura connection reset, not reproduced on retry, but consistent with this
endpoint being the most exposed to connection-pool/latency issues under load because
it holds so many connections open per request.

## Notes on check 15 (degradation guarantee) design decision

`/forecast.json` (source: live Open-Meteo HTTP feed) and `/sandboxes.json` (source:
`ingest/state/sandboxes.json` on disk) do not read from Neo4j at all, so killing the
graph correctly leaves their `meta.degraded` unchanged — that is honest behaviour, not
a bug. The validator therefore requires `meta.degraded === true` only for the seven
endpoints whose tier-1 source actually is the graph (`/health`, `/events.json`,
`/lines.geojson`, `/stations.geojson`, `/brief`, `/layers.json`, `/impact/{lineId}`),
and requires zero 5xx responses across all nine endpoints regardless of source. Both
held on every run in this investigation.

The validator also force-kills its own throwaway :8001 instance via `taskkill /F /T`
and confirms the port is free afterward (`B15-cleanup`) — an early version relied on
`Popen.terminate()`/`kill()` alone, which once left a stray `python.exe` listening on
:8001 after the script exited. That gap is now closed.
